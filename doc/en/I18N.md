# I18N.md — Okeymoney multilingual architecture

> 🌐 **Other languages:** [Español](../es/I18N.md)

Technical reference of the internationalization system (`App.i18n`) and the
step-by-step recipe to add a new language. Read alongside
[`technical.md`](technical.md) §5 (technical integration) and
[`SPEC.md`](SPEC.md) §3–§4 (product and accessibility rules, which apply
**in every language**).

**Current state**: Spanish (`es`, default) and English (`en`). The system
is designed for more than two languages, and most of the binary `es`/`en`
spots have already been generalised so extending to a third locale does
not require touching UI code — see §4. The only English-coupled piece
left is the **currency** (the euro symbol `€` is used in every locale),
because Okeymoney is a money-in-euros app and switching currency together
with language is not in v1 scope.

**Language policy**:

- **User interface (UI)**: multilingual — every text visible to the end
  user exists in every supported language (`es`, `en`…).
- **Technical code**: **always in English** — variable, function and
  JS-object names, and **crucially the keys in `strings.<locale>.js`** must
  be in English. The values of those keys are the translatable UI text,
  but the key itself is code, so it is in English.

  ```js
  // ✅ Correct — English key, values in the file's language
  // strings.es.js
  App.i18n.register({
    balanceLabel: 'Tienes',
    editHint: 'Toca el número para cambiarlo'
  }, 'es');
  // strings.en.js
  App.i18n.register({
    balanceLabel: 'You have',
    editHint: 'Tap the number to change it'
  }, 'en');
  ```

  This split keeps `App.i18n.t('balanceLabel')` readable in the source
  code, regardless of the active language.

## 0. Multi-file system

Okeymoney uses the multi-file pattern Apptonomia introduced in v4: each
language lives in **a separate file**, and `register` only populates the
slot for that locale. (Both files do load today via the static `<script>`
list — there is no conditional load yet — but the file's responsibility is
clearly one language.)

### Structure

```
strings.es.js          ← Spanish texts (registers in locale 'es')
strings.en.js          ← English texts (registers in locale 'en')

legal/strings.es.js    ← Spanish texts of the legal page
legal/strings.en.js    ← English texts of the legal page
```

### Advantages over the monolithic file

- **Independent maintenance**: a translator only edits the file of the
  language they know — they do not see the other language mixed in.
- **Cleaner diffs**: an English translation change shows only the English
  lines that changed, not the whole file.
- **Scalability**: adding a language is just creating
  `strings.<locale>.js` per scope (root and `legal/`), without touching
  the other languages.

### `strings.<locale>.js` pattern

```js
/* ============================================================
   Okeymoney — Texts (EN)
   Per-language file. Loaded synchronously from index.html
   (no document.write) before data.js and app.js so
   App.i18n.register has already populated the dictionary
   when any UI code calls App.i18n.t().
   ============================================================ */
(function () {
  'use strict';
  App.i18n.register({
    title: 'Okeymoney',
    tabs: { home: 'My money', goals: 'My goals', /* ... */ },
    // ... rest of EN keys
  }, 'en');
})();
```

The second argument of `register(dict, locale)` indicates **which language**
to register. `App.i18n.js` keeps the fallback to Spanish when a key is
missing.

## 1. Pieces of the system

```
assets/js/i18n.js            # Core: App.i18n (detection, persistence, t/pick/apply)
assets/js/money.js           # Registers its own texts per locale (money.*)
strings.es.js                # Spanish app texts
strings.en.js                # English app texts
index.html                   # Language selector (N buttons generated) + script load
legal/index.html             # Same pattern, loads legal/strings.<locale>.js
data.js                      # Locale-neutral data (ids, emojis) — text lives in strings
app.js                       # Uses App.i18n.t()/.pick()/.locale() to read/generate text
```

### 1.1 `assets/js/i18n.js` — core

```js
var SUPPORTED = ['es', 'en'];                   // activatable languages
var DEFAULT_LOCALE = 'es';                      // fallback when a key is missing or the detected language is not supported
var BCP47 = { es: 'es-ES', en: 'en-US' };       // BCP47 mapping for speechSynthesis
var LABEL = { es: 'Español', en: 'English' };   // text on the language button
var FLAG = { es: '🇪🇸', en: '🇬🇧' };            // emoji on the language button
```

- **Detection** (`detect()`): walks through `navigator.languages` and takes
  the 2-letter prefix of the first one in `SUPPORTED`. If none matches,
  it uses `DEFAULT_LOCALE`.
- **Persistence** (`locale()` / `setLocale()`):
  `localStorage['okeymoney:locale']`. A saved and supported value wins
  over detection. `setLocale()` saves and **reloads the page** (there is
  no hot re-render).
- **`register(dict, locale)`**: registers the dictionary in the given
  locale. The Okeymoney core (`assets/js/i18n.js`) already comes with
  `core.*` and `feedback.*` pre-registered for `es` and `en`. Each
  `strings.<locale>.js` extends the dictionary with its own keys.
- **`t(key)`**: looks up `key` (with dots, e.g. `'categories.food'` or
  `'core.back'`) in the active language. If missing, falls back to
  `DEFAULT_LOCALE` (Spanish). If still missing, returns the `key` itself
  (so broken keys are visible on screen). If the value is an array, it
  joins it with `', '` (meant for debugging, not for the UI).
- **`pick(key)`**: like `t`, but for keys whose value is an **array** of
  variants (e.g. `feedback.success`) — returns a random element. Used by
  `feedback.js` for the success/encouragement messages.
- **`apply(root)`**: applies `data-i18n` (→ `textContent`) and
  `data-i18n-aria` (→ `aria-label`) to every DOM node under `root`
  (default `document`). Runs on `DOMContentLoaded`. It also sets
  `document.documentElement.lang` and, if `<html>` has
  `data-i18n-title="key"`, sets `document.title = t(key) + ' | Okeymoney'`.
- **`lang()`**: returns the BCP47 code of the active locale (used by
  `App.tts.speak()` to pick the speechSynthesis voice). Backed by the
  `BCP47` map with fallback to `DEFAULT_LOCALE`.

### 1.2 Common keys (`core.*`, `feedback.*`)

Defined once in `i18n.js`; **do not redefine** them in
`strings.<locale>.js`. All subkeys are in English (technical code):

| Key | ES | EN |
|---|---|---|
| `core.back` | ← Volver | ← Back |
| `core.close` | Cerrar | Close |
| `core.next` | Siguiente → | Next → |
| `core.save` | Guardar | Save |
| `core.cancel` | Cancelar | Cancel |
| `core.understood` | Entendido | Got it |
| `core.listen` | 🔊 Escuchar | 🔊 Listen |
| `core.listenInstructions` | Escuchar las instrucciones | Listen to the instructions |
| `core.loading` | Cargando… | Loading… |
| `core.dataProtection` | Protección de datos | Data protection |
| `feedback.success` (array) | ¡Muy bien! / ¡Genial! / … | Well done! / Great! / … |
| `feedback.encourage` (array) | Casi. ¡Inténtalo otra vez! / … | Almost. Try again! / … |

### 1.3 `strings.<locale>.js` (root and `legal/`)

Okeymoney has **two scopes** of texts:

- `strings.<locale>.js` at the root: the app itself (three tabs + wizard).
- `legal/strings.<locale>.js`: the "Data protection" page (a single HTML
  file in `legal/index.html`).

Both follow the same pattern. The gold reference is `strings.es.js`.

```js
/* strings.en.js */
(function () {
  'use strict';
  App.i18n.register({
    title: 'Okeymoney',
    tabs: { home: 'My money', goals: 'My goals', /* ... */ },
    home: { balanceLabel: 'You have', /* ... */ },
    categories: { food: 'Food', /* ... */ },
    // ... rest of keys
  }, 'en');
})();
```

**Important**: the keys (`tabs.home`, `home.balanceLabel`,
`categories.food`…) are technical code and always in English, regardless
of the UI language. The values are the user-facing translatable text.

- A `title` key must always exist (used by `data-i18n-title` for the
  `<title>`).
- Keys **must match exactly** across all `strings.<locale>.js` of the
  same scope (verified by `scripts/check.js` §2).
- Nested objects work as namespaces: `tabs: { home: '…' }` is read with
  `t('tabs.home')`.
- **Never** use an array when you need positional indexing (`t()` would
  join the array with commas). For position-indexed tables, use an object
  with text keys: `{0: '', 1: 'miles', 2: 'millions'}` and read with
  `t('grupoEtq.' + i)`.
- The set of visible keys comes from the HTML (`data-i18n` /
  `data-i18n-aria`) **and** from every `App.i18n.t(...)` call in `app.js`.
  If you add a new piece of text, add the key to **every**
  `strings.<locale>.js` before merging.

### 1.4 Where the text lives: `data.js` vs `strings.<locale>.js`

Okeymoney separates "what changes per language" (visible text) from "what
does not change" (ids, emojis, amounts in cents). `data.js` contains
**only locale-neutral data**:

- `DATA.categories`: `[{ id: 'food', icon: '🍎' }, …]`. The visible name
  comes from `App.i18n.t('categories.' + c.id)`.
- `DATA.goalIcons`: emojis for goals (`['🎮', '⚽', …]`).
- `DATA.learnTeaser`: ids of the "Aprender" cards (`['change', 'budget',
  'needsWants']`). The visible text comes from
  `App.i18n.t('learn.teaser.' + id)`.

By convention, **visible text always lives in `strings.<locale>.js`**, not
in `data.js`. This keeps `data.js` truly locale-neutral — adding a language
does not require touching it.

### 1.5 HTML: `data-i18n*` attributes

```html
<html lang="es" data-i18n-title="title">
…
<h1 data-i18n="title">Okeymoney</h1>
<button data-i18n-aria="home.editBalanceAria" aria-label="Cambiar cuánto dinero tienes">…</button>
```

The Spanish text/`aria-label` is left as the HTML default content (so the
page still makes sense if `i18n.js` fails to load) and `apply()` overwrites
it on start. Attributes that `apply()` **does not** cover (set manually in
`app.js` on start): `placeholder` on `<input>` (the goal-name input uses
this) and any text generated dynamically inside a re-render.

### 1.6 Mandatory script load order

```html
<script src="assets/js/utils.js"></script>
<script src="assets/js/i18n.js"></script>
<script src="assets/js/tts.js"></script>
<script src="assets/js/storage.js"></script>
<script src="assets/js/feedback.js"></script>
<script src="assets/js/money.js"></script>
<script src="strings.es.js"></script>
<script src="strings.en.js"></script>
<script src="data.js"></script>
<script src="app.js"></script>
```

`i18n.js` loads before `tts.js`/`feedback.js`/`money.js` (they all read the
active locale). Both `strings.<locale>.js` files load synchronously
**before** `data.js` and `app.js`, so `App.i18n.register` has already
populated the dictionary by the time any UI code calls `App.i18n.t()`.
`document.write` is intentionally **not** used: Chrome and Firefox process
scripts injected via `document.write` asynchronously, which would make
`t()` return literal keys during the first render.

### 1.7 Language selector (in `index.html`)

`app.js` renders the selector buttons **dynamically** from
`App.i18n.SUPPORTED`, reading `App.i18n.LABEL` and `App.i18n.FLAG` for the
button label and flag. Adding a language does not require editing HTML —
only extend `SUPPORTED` / `LABEL` / `FLAG` in `i18n.js` (see §5).

```js
// app.js (summary)
function renderLanguageSelector() {
  var active = App.i18n.locale();
  $('#langRow').innerHTML = '';
  App.i18n.SUPPORTED.forEach(function (loc) {
    var btn = document.createElement('button');
    btn.setAttribute('aria-pressed', String(active === loc));
    btn.textContent = (App.i18n.FLAG[loc] || '') + ' ' + (App.i18n.LABEL[loc] || loc);
    btn.addEventListener('click', function () { App.i18n.setLocale(loc); });
    $('#langRow').appendChild(btn);
  });
}
```

`legal/index.html` has no language selector: by its nature (legal info
page) it is shown in the active locale and, if it ever needs to be
translated, it follows the same multi-file pattern.

## 2. Number and money format: NOT just translation

Okeymoney always works in **integer cents** (never floating-point euros)
and formats the output per locale. The key rule:

- **Decimal separator**: Spanish uses `,` (`1,50 €`), English uses `.`
  (`1.50 €`). The `DECIMAL_SEP` map lives in `assets/js/money.js` and
  must be extended when a language is added (Step 5 of §5).
- **No number scaling**: the amounts Okeymoney handles in v1 are small
  (`MAX_CENTS = 9999999` → 99,999.99 €), so the long-scale vs short-scale
  problem that Apptonomia has to deal with when reading large numbers out
  loud does not apply here. If larger amounts are ever introduced, or TTS
  is wired in, **this** is the section to revisit.
- **Currency**: Okeymoney is a euros app (`€`). Switching currency together
  with language is not in v1 scope — if it ever happens, it should be
  modelled as a `(locale, currency)` pair in a separate map, not as a
  consequence of the language.

**General rule**: before showing a number or an amount in a new language,
check how a native speaker would actually write it: thousands and decimal
separators as they really are.

## 3. Cultural content: DO NOT translate literally

Okeymoney has very little "cultural" content in v1 (the categories and
emojis are the same across languages). Still, the Apptonomia rule applies
in spirit:

- **Never** translate literally a text that depends on a pun, a rhyme or
  a cultural reference — write content genuinely of the target language
  with the same pedagogical intent.
- **Do** translate directly word-for-word what is plain vocabulary (the
  category names "Food", "Fun", "Transport", etc.).

## 4. Binary `es`/`en` spots (generalisation status)

This is the list of places that still branch by language. Adding a third
language **does not** touch them from the app side — but you must add an
entry to each map for the new locale.

| File:line | What it does | What to add when a 3rd language ships |
|---|---|---|
| `assets/js/i18n.js` `SUPPORTED` | `['es', 'en']` | Add the code: `['es', 'en', 'fr']` |
| `assets/js/i18n.js` `BCP47` | `{ es: 'es-ES', en: 'en-US' }` | Add `'fr': 'fr-FR'` |
| `assets/js/i18n.js` `LABEL` | `{ es: 'Español', en: 'English' }` | Add `'fr': 'Français'` |
| `assets/js/i18n.js` `FLAG` | `{ es: '🇪🇸', en: '🇬🇧' }` | Add `'fr': '🇫🇷'` |
| `assets/js/i18n.js` `core` / `feedback` | `es` and `en` blocks | Add a `fr` block with the same keys |
| `assets/js/money.js` `DECIMAL_SEP` | `{ es: ',', en: '.' }` | Locale-keyed map (e.g. `fr: ','` or `fr: ' '`) |
| `assets/js/i18n.js` `DEFAULT_LOCALE` | `'es'` | Untouched — always Spanish, as a safe fallback |

`app.js` and `index.html` have been rewritten to render the selector from
`App.i18n.SUPPORTED`, so no binary spots remain there.

## 5. Recipe: adding a new language (example: French, `fr`)

Each step is mechanical except step 4 (content) and step 5 (decimal
separator).

### Step 1 — Register the language in the core

In `assets/js/i18n.js`:

```js
var SUPPORTED = ['es', 'en', 'fr'];
var BCP47 = { es: 'es-ES', en: 'en-US', fr: 'fr-FR' };
var LABEL = { es: 'Español', en: 'English', fr: 'Français' };
var FLAG = { es: '🇪🇸', en: '🇬🇧', fr: '🇫🇷' };
```

Add a `fr` block to the `core` / `feedback` dictionary (same keys as `es`
and `en`):

```js
fr: {
  core: {
    back: '← Retour', close: 'Fermer', next: 'Suivant →',
    save: 'Enregistrer', cancel: 'Annuler', understood: 'Compris',
    listen: '🔊 Écouter', listenInstructions: 'Écouter les instructions',
    loading: 'Chargement…', dataProtection: 'Protection des données'
  },
  feedback: {
    success: ['Bravo !', 'Génial !', "Tu l'as fait !", 'Super !'],
    encourage: ['Presque. Essaie encore !', "Pas grave. Encore une fois !"]
  }
}
```

### Step 2 — Language selector

No change needed: `app.js` already renders the buttons from `SUPPORTED`.
As soon as the language is in `LABEL` and `FLAG`, it appears on reload.

### Step 3 — Root `strings.fr.js`

Create `strings.fr.js` at the root with the **same keys** as
`strings.es.js` / `strings.en.js` (same names, same nested structure).
Use `strings.es.js` as the gold reference for shape.

### Step 4 — `legal/strings.fr.js`

Create `legal/strings.fr.js` with the same keys as
`legal/strings.es.js` / `legal/strings.en.js`.

### Step 5 — Decimal separator

In `assets/js/money.js`:

```js
var DECIMAL_SEP = { es: ',', en: '.', fr: ',' };  // or ' ' if needed
```

If the language also uses a thousands separator (narrow space, etc.),
generalise `format()` to use it too — Okeymoney currently shows small
amounts and does not need a thousands separator.

### Step 6 — Update `sw.js`

Bump `VERSION` (`'okeymoney-v1'` → `'okeymoney-v2'`, for example) and
add the new `strings.fr.js` files to the `FILES` array:

```js
var VERSION = 'okeymoney-v2';

var FILES = [
  // … existing …
  './strings.fr.js',
  './legal/strings.fr.js',
  // … rest …
];
```

### Step 7 — Add the `<script>` tag in `index.html` and `legal/index.html`

Each `strings.<locale>.js` is loaded synchronously **before** `data.js`
and `app.js` (no `document.write`). Add the line in the same order as
`es` and `en`:

```html
<!-- index.html -->
<script src="strings.es.js"></script>
<script src="strings.en.js"></script>
<script src="strings.fr.js"></script>
<script src="data.js"></script>
<script src="app.js"></script>
```

```html
<!-- legal/index.html -->
<script src="strings.es.js"></script>
<script src="strings.en.js"></script>
<script src="strings.fr.js"></script>
```

### Step 8 — Verify key parity

`scripts/check.js` (§2) validates that **all** `strings.<locale>.js` of
the same scope (root and `legal/`) have exactly the same keys. Adding
`fr` makes the check compare 3 files without touching the script.

```bash
node scripts/check.js
```

If any key is missing in `fr`, `check.js` will list it with detail ("only
in strings.es.js: …", "only in strings.fr.js: …").

### Step 9 — Functional verification

- Language selector: the third button appears in `index.html` and the
  choice persists in `localStorage['okeymoney:locale']`.
- Reload with `fr` active: the UI is shown in French, no key falls back
  to Spanish on screen.
- Expense wizard: amounts are formatted with the correct decimal
  separator.
- Offline mode (installed PWA): the new `strings.fr.js` files are in
  the service worker's `FILES` and work without network.

## 6. What NOT to do

- Do not rely on automatic translation of numbers, amounts or
  placeholder templates without checking the real convention of the
  target language (§2).
- Do not leave a key without its equivalent in **every** supported
  language — the Spanish fallback hides the gap instead of failing
  visibly, and `check.js` will catch it in CI.
- Do not use arrays in `strings.<locale>.js` for position-indexed data
  (`t()` flattens them with `join(', ')`); use an object with text keys
  (`{0: '', 1: '…'}`).
- Do not add a new language without first extending `SUPPORTED`,
  `BCP47`, `LABEL`, `FLAG` in `i18n.js` and `DECIMAL_SEP` in `money.js`
  (§4): otherwise the new language silently inherits the default
  language's behaviour.
- Do not translate literally categories or goal names that depend on a
  pun or a cultural reference — write content of the target language
  with the same pedagogical intent.
- Do not add a `<script>` for a `strings.<locale>.js` after `data.js` or
  `app.js`: `App.i18n.t()` would return the literal key during the first
  render.
- Do not forget to bump `VERSION` in `sw.js` and add the file to
  `FILES` when creating a new `strings.<locale>.js`: installed PWAs
  on the old version would not download it until the cache is cleared.
